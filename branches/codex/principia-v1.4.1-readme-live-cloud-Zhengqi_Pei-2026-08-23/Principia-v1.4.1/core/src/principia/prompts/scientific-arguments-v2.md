Normalize eligible Evidence Claim Atoms into zero to eight Scientific Arguments under scientific-principle-v2. Return one JSON object matching the schema.

A Principle is an evidence-grounded, atomic, transferable scientific argument about a relationship, mechanism, constraint, trade-off, design rule, empirical regularity, or theoretical relation, together with its applicability boundary. It must remain meaningful after removing references to the paper and its authors.

Reject rather than recast novelty, priority, contribution, feature-list, benchmark, document-summary, and author-self claims. A paper, study, author, dataset, benchmark, or named model cannot be the scientific subject. A method description qualifies only if the evidence supports a transferable relationship or design rule. Do not turn correlation into causation, add a comparison, or broaden a population.

Reject vague forecasts such as a technique being expected to play a central role, transform a field, become important, or provide a promising future direction. A hypothesis qualifies only when it states a concrete, evidence-anchored, testable scientific relation with explicit conditions; rhetoric about future importance does not.

Do not discard a supported observed or formal relation merely because its source sentence names a method. When another supplied atom describes that method's mechanism, normalize the subject to that source-grounded mechanism (for example, an adaptive verification policy), and support the argument with both atoms. This is allowed neutralization, not unsupported generalization. Keep the result study_bound unless independent Works corroborate it.

For a results-bearing atom, actively recover the scientific relation already present in its exact evidence: identify the scientific system, driver or intervention, outcome, direction, and tested conditions. Emit separate atomic arguments for distinct supported relations; do not collapse a paper into one summary. Return zero arguments only when every supplied atom is metadata, priority rhetoric, an unsupported method description, or otherwise lacks a driver-to-outcome, constraint, trade-off, regularity, or formal relation.

When the source does not state an explicit applicability boundary, set boundary_provenance to conservative_study_limit, generalization_level to study_bound, and use a narrow boundary such as "limited to the sampled system and reported experimental conditions". This boundary is a server-visible conservative limit, not a source claim. A generated operational test may use testability_provenance generated_challenge. These two conservative fields must never be mapped as source-grounded evidence.

The top-level output is {"arguments":[...]}. Each field_support item has exactly two keys: field and atom_ids. Use the exact atom IDs supplied in the input. Provide field_support assignments for canonical_claim, subject_system, driver_or_intervention, outcome, direction_or_qualifier, and conditions; also provide boundary only when boundary_provenance is source_grounded. Do not output Evidence Atom objects, quotations, assertion labels, a map keyed by quotation, or JSON Schema metadata.

Produce one argument for each distinct atom or compatible atom group that already states a relationship, mechanism, constraint, trade-off, intervention effect, empirical regularity, or formal relation. Remove document rhetoric while retaining the exact scientific system, driver, outcome, direction, qualifiers, and conditions. For example, normalize "We find that independent verification reduces selection error when verifier and generator failures differ" into a study-bound argument whose subject is the inference pipeline—not the paper—and whose claim retains the stated condition.

Every scientific claim field must map to one or more supplied atom_ids through field_support. Never repeat or output segment_key, quotation, or supported_fields: the server resolves exact quotations from atom IDs after validation. Give each field_support item exactly one field and the atom IDs that support it.

When the source states an applicability boundary, set boundary_provenance=source_grounded and include a boundary field_support assignment. When no external boundary is stated, do not discard an otherwise supported relation: set boundary_provenance=conservative_study_limit and use a narrow epistemic boundary such as "Evidence is limited to the reported system, task, population, and conditions; transfer beyond them is unestablished." This conservative limit is not a new scientific fact and must not receive a boundary field_support assignment. One-work arguments are always study_bound. Cross-study arguments require compatible atoms from at least two independent works. A generated testability clause must be labelled generated_challenge and must not masquerade as source text.

Return an empty arguments list only when the atoms are metadata, summaries, unsupported method descriptions, or assertions without a transferable scientific relationship. Never optimize for output count, but do not reject a supported relationship merely because its safe boundary must be conservative.
